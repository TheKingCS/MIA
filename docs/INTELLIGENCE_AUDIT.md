## 3. What's missing (against the spec's phases)

1. **Capability registry at run time** (Phase 2B): a queryable list of
   features with status (implemented / partial / planned), their tools,
   permissions and limits, generated from the code (the Apps list, the
   tool registry, the action kinds) and checked by tests, so MIA can
   answer "can you do X?" truthfully.
2. **Repository and spec retrieval** (Phase 2C, 3): an index of
   `docs/` (decisions, current state, specs) and code symbols, refreshed
   when files change, with source references; answers cite files.
   Keyword first (it's what works on the phone), embeddings only if the
   evaluation shows keyword misses.
3. **Operational knowledge** (Phase 3.4): recent errors and health
   ("why did that fail?") from the log and the action history.
4. **Multi-step orchestration** (Phase 4): today a turn is one tool call
   (plus follow-ups); "gather, plan, act, check, report" needs a small
   loop with a step limit and every change still through approval.
5. **Self-improvement workflow** (Phase 7): MIA proposing a change
   (plan, files, risks) and, with approval, Claude or a sandboxed worker
   implementing it on a branch with tests. The approval rules in the
   spec match the ROADMAP's staged plan; nothing here should let MIA
   grant itself anything.
6. **Evaluation additions** (Phase 9): identity, capability honesty, "I
   can't do that yet" instead of fabricating, retrieval accuracy.

## 4. What gets reused

The tool registry and its routing; `direct_lookup` for facts that must
not be phrased wrong; the action contract for every change; Life State
for the picture of the person's life; user-help retrieval as the
retrieval pattern; the golden set and live check for evaluation; the
home link for routing between the phone and the PC.

## 5. Plan, in increments (each its own approval)

1. ✅ **Slice 1, built: MIA knows her model** (section 6).
2. **Capability registry**: `core/capabilities.py` builds, from the code,
   each app's status, tools (read / change), permissions and known
   limits (from `docs/WEB_PARITY.md` and the apps list); a
   `what_can_you_do` / `can_you` tool answers from it; a test fails when
   a feature is added without an entry.
3. **Docs retrieval for MIA about herself**: index `docs/` (decisions,
   current state, the specs, the guides) by heading; `how_does_mia_work`
   answers with the passage and its file; current state ranked above
   history, plans labelled as plans.
4. **Code retrieval**: symbols and docstrings from `core/` (Python's
   own `ast`, no new dependency), answers cite `file:line`; secrets and
   personal data never indexed (`data/`, `config/config.json`, vaults).
5. **"Why did that fail?"**: the last errors and refused actions, from
   the log and the action history, in plain words.
6. **Multi-step turns**: up to N tool steps, reads freely, changes only
   as proposals for approval; the evaluation decides N.
7. **Dev workflow** (ROADMAP stage 2): MIA writes a proposal (what,
   which files, risks, tests) into `docs/HANDOFFS/` for Claude; no code
   changes by MIA herself.
8. Routing by measured quality (Phase 8) only if the evaluation shows a
   need; fine-tuning only after that, never for facts.
