# Testing Guide — 4.1 Reference Library Engine

## What changed

- `core/reference_library_manager.py` — new core service
  (`AppContext.reference_library`) wrapping `libzim`. Discovers `.zim`
  packs in a configurable folder, reads main pages/entries/resources,
  and searches within a single pack.
- `config/default_config.json` — new `reference_library.root_path` key
  (defaults to `""`, which resolves to `reference_library/` at the repo
  root — see the manager's own docstring for why that's deliberately
  not under `data/`).
- `requirements.txt` — new `libzim` dependency.
- `.gitignore` — `reference_library/*` ignored, same pattern as `data/`.

**No UI yet.** This milestone is the engine only — there's no menu
screen to click through. `modules/knowledge`'s placeholder is
unchanged; that upgrade is milestone 4.2. This guide is therefore a
Python-console smoke test plus the automated suite, not a
click-through checklist.

## Part 1 — Automated tests

```bash
pytest tests/test_reference_library_manager.py -v
```

**Expected:** all tests pass, covering pack discovery, a corrupt
`.zim` being skipped (not crashing), main-page/entry content
retrieval, and in-pack search — all against tiny `.zim` fixtures built
on the fly with `libzim.writer` (no bundled binary file, no network
access needed).

## Part 2 — Manual smoke test with a real content pack

The automated tests use synthetic fixtures; this part confirms the
engine against a real Kiwix ZIM file, which is worth doing at least
once before trusting 4.2's UI to be built on solid ground.

1. Get a small real `.zim` file. Kiwix publishes a library at
   <https://library.kiwix.org/> — pick something small (a few MB) for
   a quick test, e.g. a short WikiHow or Wikipedia-selection pack.
2. Copy it into `reference_library/` at the repo root (create the
   folder if `python main.py` hasn't been run yet to auto-create it).
3. From the repo root, with `.venv` active:

   ```bash
   python3 -c "
   from core.app_context import AppContext
   from core.config_manager import ConfigManager
   from core.event_bus import EventBus
   from core.reference_library_manager import ReferenceLibraryManager

   ctx = AppContext(config=ConfigManager(), events=EventBus())
   mgr = ReferenceLibraryManager(ctx)

   packs = mgr.list_packs()
   print('Packs found:', [(p.pack_id, p.title, p.article_count) for p in packs])

   pack_id = packs[0].pack_id
   main_page = mgr.get_main_page(pack_id)
   print('Main page path:', main_page)

   content, mimetype = mgr.get_entry_content(pack_id, main_page)
   print('Mimetype:', mimetype, '- content length:', len(content))
   print(content[:300])

   hits = mgr.search(pack_id, 'the')
   print('Search hits for \"the\":', [(h.path, h.title) for h in hits[:5]])
   "
   ```

   **Expected:** the pack shows up with a sensible title (from the
   ZIM's own metadata, not just the filename), the main page returns
   real HTML content, and the search returns at least one hit for a
   common word.
4. Replace the `.zim` file with a `.txt` file renamed to `.zim` (or
   any garbage file with a `.zim` extension).
   - **Expected:** `list_packs()` returns the file skipped (not
     present in the result), and nothing crashes. Check
     `logs/mia.log` for a `Skipping unreadable ZIM file` warning.
5. Remove `reference_library/` entirely (or point
   `reference_library.root_path` in `config/config.json` at a path
   that doesn't exist/isn't mounted).
   - **Expected:** `list_packs()` returns `[]`, no crash, and the
     manager recreates the folder on next construction if the parent
     is writable.

## Design notes worth knowing before building 4.2

- `archive.main_entry.path` is a synthetic `"mainPage"` alias that
  `get_entry_by_path` can't look up directly — `get_main_page()`
  resolves through the redirect to the real, fetchable path. Don't
  "simplify" this to `archive.main_entry.path` directly; it'll return
  a path that then 404s against `get_entry_content()`.
- `get_entry_content()` is intentionally generic (any entry path, not
  just articles) — 4.2's `QTextBrowser` resource-loading hook for
  inline images/CSS should call the same method as the article viewer,
  not grow a parallel resource-fetching path.
