# Testing Guide — 2.8 Update Manager

## What changed

- `core/update_manager.py` — new: `apply_update_package()` /
  `peek_update_manifest()`. Validates and applies an offline update
  package (see `docs/UPDATE_PACKAGE_SPEC.md`), staging into a temp
  directory before touching any live project file. If the project is a
  git working tree, a successful update is auto-committed — staging
  only the files the update itself touched, never a blanket `git add -A`.
- `modules/settings/module.py` — new "Update Manager" section with an
  "Apply Update Package..." button.

**Heads up — unlike every other feature tested so far, this one
actually modifies real project files and creates a real git commit
when run for real.** There's no dedicated "isolated" mode in the app
itself; the isolation lives in the automated tests
(`tests/test_update_manager.py`, which run against a throwaway repo in
a temp directory, never this real one). Build any test package you
manually apply with that in mind — see Part 1 below for a safe pattern
(a package that only adds a new, harmless file).

## Part 1 — Build and apply a safe test package

```bash
mkdir -p /tmp/mia_update_test/docs/testing
cat > /tmp/mia_update_test/update_manifest.json <<'EOF'
{
    "app": "MIA",
    "manifest_version": 1,
    "target_version": "0.2.x-test",
    "description": "Test update — adds a harmless marker file."
}
EOF
echo "test marker" > /tmp/mia_update_test/docs/testing/_update_test_marker.txt
python3 -c "
import zipfile
from pathlib import Path
src = Path('/tmp/mia_update_test')
with zipfile.ZipFile('/tmp/mia_update_test.zip', 'w') as zf:
    for f in src.rglob('*'):
        if f.is_file():
            zf.write(f, f.relative_to(src))
"
```

1. Run `python main.py`, go to **Settings**.
2. Click **⬆ Apply Update Package...**, select `/tmp/mia_update_test.zip`.
   - **Expected:** a **Confirm Update** dialog showing the target
     version and description from the manifest, plus a security
     warning about modifying application files.
3. Click **Yes**.
   - **Expected:** an **Update Applied** dialog: "Applied 1 file(s)."
     plus a note that a git commit was created for rollback (assuming
     this project is a git repo, which it is), plus a restart reminder.
4. Verify directly:
   ```bash
   cd ~/Projects/MIA
   cat docs/testing/_update_test_marker.txt   # should show "test marker"
   git log -1 --stat                           # should show the new commit,
                                                 # touching only that one file
   git status                                   # any *other* uncommitted work
                                                 # you had should be untouched
   ```

## Part 2 — Reject a non-update file

1. `echo "junk" > /tmp/not_an_update.zip`
2. Click **⬆ Apply Update Package...** again, select that file.
   - **Expected:** either an immediate clear rejection, or a confirm
     dialog with generic "(Could not read update details...)" text
     followed by an "Update Failed" dialog after confirming — either
     way, no crash, and `git status` / project files unaffected.

## Part 3 — Confirm the "no unrelated files swept in" guarantee

This is the most important safety property to confirm, since it's what
makes the auto-commit trustworthy as a rollback point.

1. Make sure you have *some* unrelated uncommitted change sitting in
   the tree first (e.g. touch a scratch file, or just use whatever's
   already uncommitted from other work).
2. Apply a test update package (Part 1's pattern).
3. `git status` afterward.
   - **Expected:** the update's own file is now committed (clean), but
     your unrelated uncommitted change is **still uncommitted** —
     `git add -A` was deliberately not used; only the update's own
     files were staged.

## Cleanup

```bash
cd ~/Projects/MIA
git rm docs/testing/_update_test_marker.txt
git commit -m "Remove update-manager test marker"
rm -rf /tmp/mia_update_test /tmp/mia_update_test.zip /tmp/not_an_update.zip
```

## What to report back

- Did the confirm dialog show manifest details (Part 1)?
- Did the applied update land correctly and create a git commit
  touching only its own file?
- Did a non-update file get rejected cleanly (Part 2)?
- Did unrelated uncommitted work survive untouched after applying an
  update (Part 3) — this is the property that makes the rollback
  commit trustworthy?
